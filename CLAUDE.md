# Queenie's Playland (JS13K entry)

A carnival-games WebGL2 game — prize wheel, water-gun target, whack-a-mole — built for
the [js13kgames](https://js13kgames.com/) competition. The zipped submission (one
`index.html`) must fit under **13,312 bytes (13 KB)**, and the current package sits
within a few hundred bytes of that. This single constraint drives most of the tooling
and a good chunk of the code style described below. When in doubt about *why* something
looks unusual, assume it's in service of that byte budget.

Bun is the runtime and package manager; there is no npm/nvm/node step anywhere.

## Running it

```sh
bun install
bun run dev          # Vite dev server, readable ESM, DEV-only tooling enabled
bun run pack         # the real thing: build -> Roadroller -> one HTML -> zip -> size report
bun run breakdown    # where the ZIP bytes go, module by module (measured, not estimated)
bun run pack:tune    # occasionally, after a big change: re-search Roadroller params (~45 s)
bun run test:engine  # pack + headless verification of the parser and runtime
```

`bun run pack` is the ground truth for size. Its report ends with `N bytes to spare` or
`OVER by N` — quote that number, not the raw bundle size, when talking about cost.
`bun run build` is Vite's ordinary ESM build into `dist/` and is *not* the entry.

## Architecture

Standard Vite + ES modules in `src/`, bundled by `vite.js13k.config.ts` into a single
**IIFE** chunk (Roadroller's output is a classic self-extracting script, so the bundle
must run without module semantics; dynamic imports would become a second file the
inlined HTML can't fetch). Tree-shaking is real here: an exported entity, stage,
easing or SFX that nothing imports costs zero shipped bytes — which is why several
files deliberately have **one export per item** rather than one combined table.

Runtime shape:
- `engine.js` — tiny WebGL2 engine around one shader pair (`shaders/model.vert` /
  `model.frag`), two textures (colour-index + palette), interleaved VAOs, DOMMatrix
  math. It's **instanced**: `draw()` queues copies (world matrix + colour override in
  divisor-1 attributes) and `flush()` issues one `drawArraysInstanced` per distinct
  mesh, so draw calls scale with mesh *variety*, not object count. `main.js` makes two
  engines: `E` for the world canvas and `H` for the `#hud` canvas (text/HUD rects are
  instanced quads too).
- `pico.js` — picoCAD2 `model.txt` parser to GPU-ready interleaved vertex data
  (`STRIDE` = 10 floats). Pure JS, no DOM/GL, testable headless. Node rotations in the
  model file are **radians**. Decodes the build's compact `pc2!` payload transparently.
- `entity.js` — blueprints: an array of parts `{ mesh, pos, rot (degrees), scale, color?,
  uv?, parent? }`. A part with **no `mesh` is a pivot** (draws nothing; exists so children
  rotate/scale about it). `trs()` is THE one definition of translate→rotate→scale; every
  other transform (parts, stage placements, editor gizmos) composes through it.
  `spawnEntity` bakes local matrices once; `drawEntity` just queues `world * local`.
- `entities.js` / `stages.js` — **generated by a Blender addon** (`tools/blender/
  pc2_entity`, not in this checkout) and safe to hand-edit between exports. A blueprint's
  trailing `NAME.t = '...'` is its tag (role); `NAME.s` holds authored pose states.
  Stages are flat placement lists `{ e, p, r, s, c, b }` with identity fields omitted;
  `b` picks a palette bank so two copies of one blueprint can wear different colours.
- `anim.js` — one stateless `tween(now, ...)`; easings shape the value, modes (`once`,
  `cycle`, `repeat`) shape time. Everything is a pure function of the clock.
- `camera.js` — camera is data (`at`, `yaw`, `pitch`, `dist`, `shake`); nothing turns it
  back into an orbit control. `game_view.js` is the shared fixed framing.
- `sfx.js` / `sfx_bank.js` — PICO-8 SFX synth (168-char hex strings) + WebAudio
  playback. The bank has one export per slot for the tree-shaking reason above.
- `main.js` — game state, the three stages, HUD text (a 1-bit hex font), input, the RAF
  loop, and a lot of `if (import.meta.env.DEV)` tooling (entity editor, orbit camera,
  `?win`, screenshot key).

## Code style

- **Plain JS, no TypeScript** in `src/`; TS is used only for tooling (`tools/**`,
  `vite.js13k.config.ts`). Game code stays untyped on purpose so nothing constrains how
  aggressively it gets renamed/rewritten at build time.
- `src/` uses 2-space indentation, semicolons, `const` arrow functions for free functions,
  short single-letter names for hot locals (`E`, `H`, `p`, `c`) and SHOUTY names for
  tuning constants at the top of a section. `tools/` uses 4 spaces. Match the file
  you're in.
- **Comments explain *why*, and they're free** — comments, whitespace and readable
  names cost nothing after minification, so don't golf source for size. Several files
  carry long header comments recording *measured* outcomes (e.g. "packing texture pixels
  2-per-byte GREW the zip by 328 bytes"). When you learn something like that, record it
  the same way, next to the code it protects.
- **Dev-only code is gated by `import.meta.env.DEV`**, never a runtime flag. Vite
  replaces it with `false` for the pack and esbuild deletes the branch, so it's free to
  add checks, editors, asserts and logging behind it. `DEBUG` in `main.js` is a second,
  hand-toggled switch *inside* DEV for the noisier diagnostics.
- Write normal booleans/`const`/`null`; esbuild handles `true`→`!0` etc. Don't hand-roll
  micro-minification — measure structural changes instead (fewer statements, fewer
  distinct names, shared helpers).
- Keep `index.html` tiny and free of single-letter element ids and inline scripts:
  Roadroller runs with `-D` (decoder state in single-letter globals, worth ~23 zip bytes)
  and that is only safe while the page has neither. If you add either, drop `-D` in
  `tools/js13k/pipeline.ts` and re-measure.

## Size pipeline (tools/js13k, tools/vite)

`bun run pack` runs, in order: Vite build (with two build-only plugins) → Roadroller
with **pinned** parameters → inline into one HTML → hand-written zip with zopfli →
report. Dev serves everything raw, so dev and pack can never disagree about a format.

- **`tools/vite/glsl_min.ts`** — strips comments/whitespace from `*.vert?raw` /
  `*.frag?raw` at build time. Shader source rides inside a JS string that no JS minifier
  touches, so GLSL comments would otherwise ship verbatim. Comment shaders freely.
- **`tools/vite/picocad_compact.ts`** — re-encodes any `*.txt?raw` that parses as a
  picoCAD2 model into positional tuples with bit-packed flags and rounded floats
  (`pc2!` prefix). Texture pixels are deliberately left as one hex digit each (see the
  header comment for the measurement). Positions round at 1e8, not less — scale
  amplifies vertex error.
- **`tools/vite/data_round.ts`** — rounds the Blender-exported numbers in `entities.js`
  / `stages.js` at build time: 1 decimal for ordinary values, 2 for values under 1 and
  for exact quarters like `1.25` (`DATA_DIGITS` / `DATA_FINE`); the authored files keep
  all four. The ladder is measured in the config comment — the two exceptions are what
  make 1 decimal safe: small offsets under a big parent scale sink eyes into heads, and
  hand-authored quarters round the wrong way (the wheel pivot's `1.25` → `1.3` lifted
  the whole wheel 6 px). Because the pack rounds and dev doesn't, `verify_runtime.ts`'s *dev vs packed* comparison is
  expected to report a couple of thousand shimmering pixels per frame — compare against
  a saved package instead when checking a pipeline change.
- **Terser with a property-mangling whitelist** (`MANGLE_PROPS` in
  `vite.js13k.config.ts`). The pack minifies with Terser rather than esbuild (that swap
  alone was −202 zip bytes) and renames the property names listed in `MANGLE_PROPS`
  everywhere they appear — blueprint keys (`mesh pos rot color parent uv`), engine mesh
  records, camera fields, the picoCAD parse tree (another −195). Minifiers leave property
  names alone because one might belong to the browser, so the list is *only* names that
  are ours on every object they touch; the comment above it records what's excluded and
  why (`scale` is a DOMMatrix method, `min`/`max` are on `Math`, ...). Two rules follow:
  **never reach a listed property through a string** (`p['pos']`, a table of key names,
  `'pos' in p`) — the string keeps the old name and the read silently returns
  `undefined`; and when a new hot property name appears, add it to the list and re-verify.
- **Roadroller, pinned** (`pipeline.ts` `TUNED`): the default optimizer is a time-boxed
  search and lands ±85 bytes run to run, which is bigger than most experiments. `-O0`
  plus the found parameters makes every pack byte-identical for the same input. Re-tune
  only with `bun run pack:tune`, which packs *both* candidates and prints an exact
  `TUNED` replacement only if the new search wins on real ZIP bytes (Roadroller's own
  estimate disagrees with the zip often enough to matter). `-D` is separate (see above).
- **Inline + zip** (`pipeline.ts`, `zip.ts`): drops `<script src>`, minifies the
  markup, appends the rolled script, zips with zopfli (zlib-9 floor) using fixed
  timestamps so identical input → identical bytes.
- **`bun run breakdown`** — prices a module (or a `// --- section ---` region inside
  one, or the model payload) by *cutting it out and re-running the real pipeline*.
  Numbers are marginal (modules share one compression context; the table won't sum
  to the total) and there's a ~740-byte floor (zip headers, HTML shell, decoder) that
  belongs to nothing. Use it before optimising anything: intuition about compressed
  size is usually wrong here.

## When adding code

- **Measure, don't guess.** Run `bun run pack` before and after anything nontrivial and
  report the ZIP delta. Repeated long strings/identifiers cost far less than they look
  (Roadroller models them well); novel data — coordinates, hex, new logic — costs far
  more. `bun run breakdown` tells you where the weight actually is. Measured example:
  hoisting `Math.*` into single-letter locals (a classic js13k trick) cut the raw bundle
  by 273 bytes and *grew* the zip by 36. Don't retry it.
- **Verify any change to the pack pipeline against a saved package.** Copy
  `dist13k/index.html` somewhere before the change, then after it run
  `bun tools/js13k/verify_runtime.ts <that file>` — it drives both in headless Chrome
  and diffs frames pixel-for-pixel. Expect `12/12 identical frames` against the saved
  package for a change that shouldn't alter output (the `dev` row differs slightly by
  design — see `data_round.ts`). A wrong mangle throws no error; it just draws the wrong
  thing, and this is what catches it. (Its final "picking after resize" section tests the dev server, not
  the package, and currently fails independently of the pack.)
- New entities, stages, easings and sounds: **one `export const` each**, imported only
  where used, so unused ones tree-shake. Never merge them into a shared table.
- New blueprints follow the part schema in `entity.js`; pivots are parts without
  `mesh`; author child sizes in parent space; rotations are degrees in
  `DOMMatrix.rotate` order. Parsing or authoring picoCAD data in radians is the one
  place the two conventions meet — don't let it leak.
- Anything for authoring, debugging or verification goes behind `import.meta.env.DEV`
  (or into `tools/`), never into the shipped path.
- Keep the two engines' shared constants shared (`DEFAULT_TILE_SIZE`, `STRIDE`, `TEX_W`
  are imported by the tools rather than retyped) — two copies of a number is a bug
  waiting to happen.
- The 13 KB limit is hard, not aspirational. If a feature doesn't fit, the answer is a
  measured trade, not a hope that Roadroller will absorb it.
